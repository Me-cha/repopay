# Third-party issue sponsorship: research and integration proposal

Research update: 2026-11-07. **Research and proposal, not an accepted financial-policy decision or authorization to implement.** The user clarified the core requirement: any third party affected by an existing GitHub issue can start a bounty pool for that issue without a maintainer creating a bounty or approving that individual pool. Other people can add funds. Developers compete openly, and the existing first-qualifying-merged-PR rule determines the winner. A PR-specific reward or an unconditional tip is not the requested feature.

## The user journey

For example, `project/repo` issue #42 has been open for a year. A dependent project starts a $40 pool directly from its GitHub issue URL. Two others add $25 and $10. The displayed confirmed reward becomes $75 only after all three separate PayPal captures are verified. Contributors submit competing linked PRs. The first qualifying merged PR wins the pool under the current stable ordering; eligible contributors to that PR receive the award, with missing payout details handled as a pending claim. The original issue maintainer did not create or approve the pool. These amounts are illustrative, not live payment evidence.

The person contributing money is a **financial sponsor**. The repository owner who authorizes Copilot usage is a **review sponsor**. Paying into the pool does not give the financial sponsor permission to merge, choose a winner, access a private repository or charge their own Copilot account. The issue can exist without any prior Repopay bounty. If a maintainer-funded bounty already exists, its historical terms remain intact; an added community pool requires a shared winner decision and separate accounting.

## Current implementation and impact

- `packages/server/src/actions/create.ts` creates a draft only from an authorized maintainer command/label; an issue with no bounty has no financial record or funding link. A new third-party pool creation route must resolve the GitHub issue directly and create a distinct pool without pretending the actor has maintainer permissions.
- `actions/guards.ts` requires current repository write access for funding; `http/fund.ts` uses that authorization. Third-party payers therefore cannot currently fund, even when they can read the issue.
- `actions/fund.ts` requires an OPEN bounty, fixed bounty amount and no existing active attempt. `db/schema.ts` enforces one active non-cancelled bounty per issue and one active funding attempt per bounty. `bounties` retains a single funding actor, current attempt and capture. `settlement/award.ts` commits one award exactly equal to the frozen bounty amount. `settlement/refund.ts` ties its decision to a single original capture/funder. A real pool therefore needs a separate contribution and capture per sponsor; changing the one bounty amount is insufficient.
- `domain/funded-terms.ts` freezes issue criteria, amount, creator identity, policy and repository-owner Copilot sponsor. `verifier/collect.ts`, `settlement/settle.ts` and `settlement/award.ts` exclude `createdByGhId` from eligible contributors. If a third party becomes the bounty creator, that exclusion changes who can win; creator, funder and repository maintainer must be separate roles and the exclusion policy explicitly decided.
- Current single-funder/first-qualifying-merge rules, independent cancellation review, protected awards and existing historic terms remain intact. Preserve the existing GitHub issue context and review/CI/selection logic; the financial change must not silently alter prior commitments.

## Approaches and recommendation

| Approach | Behavior | Tradeoff |
| --- | --- | --- |
| **Recommended: one issue pool with separate contributions** | Anyone can create the pool from an existing issue; each sponsor pays separately; one qualifying merged PR wins the confirmed total. | Matches the requested product. Requires a contribution ledger, capture-specific refunds, cutoff and immutable award snapshot. |
| Independent issue commitments displayed as one total | Each sponsor has a separate financial promise to the same issue and winner. | Keeps captures isolated but can produce several awards/payouts, so winner and total must still be coordinated. |
| Extend the existing single-funder bounty row | Change its amount and funding actor on each contribution. | Reject. The current schema, frozen terms and refund logic assume one funder/capture and would lose payment identity. |

Creation must be self-service for third parties. For an existing public issue with no Repopay bounty, the sponsor enters its URL, signs in and starts the pool directly. A maintainer does not need to issue `/bounty create`, choose its amount or approve the individual pool. For an issue with a maintainer-funded bounty, keep that historic agreement intact and show separately accounted community contributions. A shared winner determination is needed so two financial aggregates cannot select different PRs in a race.

## Proposed flow

1. A sponsor pastes an existing issue URL. Resolve canonical repository/issue IDs; verify it is an open issue rather than a PR and no duplicate active pool exists. Freeze the issue's criteria, revision, participation, CI, payout and cancellation terms when the first contribution is accepted. Later sponsors explicitly accept the same terms; a subsequent issue edit does not silently rewrite them.
2. The sponsor signs in and starts a pool without per-issue maintainer approval. A separate `start_pool`/`contribute` authorization checks GitHub identity and the issue's public visibility or the user's private-repo access; it never grants maintainer authority.
3. The GitHub App must have repository access for bot comments, PR discovery and CI. The owner must separately authorize Copilot review usage. Those are integration and billing prerequisites, **not permission for each issue bounty**. If they are missing, an unpaid pool draft or pledge can be displayed, but do not capture or advertise secured money until the repository is ready; otherwise money may remain held indefinitely waiting for an owner who never opts in.
4. Each funder sees the exact issue, frozen terms, their amount, fee treatment, winner rule and refund conditions; their authenticated, CSRF-protected, single-use confirmation creates a durable contribution intent. Each gets a separate PayPal order/capture with stored request keys. Browser returns and comments are advisory. Only a verified completed capture increases the displayed confirmed reward.
5. Existing issue-wide PR discovery, exact-revision evidence, CI, Copilot review and stable first-qualifying-merge order decide the winner. The pool must close new contributions before or atomically with award commitment, reconcile in-flight captures, and freeze the exact included contribution IDs and cents. A late capture enters explicit reconciliation, not a silent extra award.
6. Commit one pool winner and exact-cent recipient allocation; deliver through encrypted contributor connections with durable per-item payout identity. A missing connection yields AWAITING_CLAIM. Existing maintainer bounty awards, when compatible, must use the same winner decision and remain separately accounted. Sponsor receipts and the issue bot comment distinguish captured reward, committed award and delivered payout.

## Pool accounting required from the start

Several supporters funding one issue is the core requirement. Add `bounty_pools` keyed by canonical repository/issue identity with one active-pool constraint and versioned frozen terms. Add `pool_contributions` with separate sponsor identity, amount and state; child payment attempts preserve each provider order/capture, keys and irreversible submission boundary. A `pool_award` records the one winning submission, evidence and immutable included-contribution set and exact-cent allocation. Append-only journal entries record funded, reserved, refunded, reversed and disputed amounts. Unique constraints and transaction locks prevent duplicate pool start, duplicate capture allocation, award/refund conflicts and double payout.

Define one **funding cutoff** and a single immutable award snapshot: which completed captures qualify, how pending/late captures are handled, and how concurrent captures and merge events are fenced. If a late capture arrives despite the cutoff, it enters a visible reconciliation path; do not silently add it to an already committed award or blindly send a refund. The existing maintainer bounty's original terms/hash/amount stay unchanged. A compatible pool can create a separate obligation for the same winning submission. If terms or candidate state conflict, block the combined award and require a reviewed decision.

Multiple contributions also change cancellation: each refund must refer to its own original capture, conflict checks must include **all** relevant financial sponsors, and no single payer may independently reclaim a contribution when that violates the shared contributor protection. Preserve the existing notice, independent review, evidence and committed-award rules; make new conflict, partial-refund and chargeback policies explicit before implementation. If the pooled reward produces multiple recipient payouts, record exact-cent allocation and uniquely identify each payout. A provider reversal or dispute after payout creates an operational liability; it must not erase the contributor's award.

## Public/private access and product controls

Public repositories are the recommended first scope. The app being installed is a repository integration prerequisite, not per-issue maintainer approval. Installation access is not third-party user access. For private repositories, verify the sponsor's current access using their own GitHub authorization on each relevant read and prevent information leaks through IDs, projections, notifications or cache. Decide what minimal payment receipt the payer can see after repo access is revoked. See [GitHub App access](https://docs.github.com/en/apps/using-github-apps/about-using-github-apps) and [permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps).

Define who can request sponsorship, whether the sponsor can also solve the issue, whether the maintainer who creates the draft remains ineligible, how repo/issue closure and app uninstall are handled, and how sponsor visibility and communications work. Avoid implicit authority: third-party payment never grants GitHub write access or control over the maintainer's review budget.

## PayPal and money constraints

- A [PayPal order](https://developer.paypal.com/platforms/checkout/standard/integrate/) is a payer-to-merchant transaction. Capture and subsequent contributor Payout are separate; a local ledger does not prove segregated or escrowed funds. PayPal [Payouts fees](https://developer.paypal.com/payouts/fees/) are paid by the sender; checkout fees, reserve, FX, loss and chargeback exposure also require a clear operator policy. State whether the advertised amount is the charge or the recipient reward and who covers any difference.
- The [authorize-and-capture window](https://developer.paypal.com/checkout/delay-capture/) is bounded, not an indefinite reservation. PayPal's [delayed disbursement](https://developer.paypal.com/platforms/checkout/delayed-disbursement/) requires approved partner/seller setup and automatically releases after 28 days; it is not a general indefinite-hold solution.
- Sandbox tests establish API behavior, not approval of a live custody model. Confirm the actual merchant entity, country, permitted activity, reserves and payout/dispute arrangements with PayPal and qualified counsel before real-money operation. PayPal's [India agreement](https://www.paypal.com/in/legalhub/paypal/useragreement-full) is country-specific; do not infer a universal approval or prohibition.
- [Refunds target the original capture](https://developer.paypal.com/checkout/refund-payment); never route refunds to a sponsor-entered address. Preserve per-operation identity and bounded retry deadlines: PayPal [Payouts sender-batch deduplication](https://developer.paypal.com/api/payments.payouts-batch/v1/definitions/sender_batch_header/) documents a 30-day window, while other endpoints have different limits. An unknown result beyond its safe retry window remains held for reconciliation.
- Distinguish per-item SUCCESS, PENDING, UNCLAIMED, RETURNED, FAILED and ONHOLD; batch success is not proof of every recipient's receipt. See [Payouts item statuses](https://developer.paypal.com/api/payments.payouts-batch/v1/definitions/transaction_enum/) and [webhook events](https://developer.paypal.com/payouts/webhooks/). Verify signatures, deduplicate deliveries and reconcile provider reads.

## Integration and validation plan

1. Record an accepted ADR defining self-service pool creation on any existing eligible issue, multi-sponsor contributions, contributor eligibility, fee responsibility, cutoff, existing-bounty compatibility and independently reviewed refunds. Preserve legacy frozen terms and ADR 0001 contributor protection.
2. Add pool/contribution/attempt/award migrations, separate financial sponsor identity from maintainer and Copilot sponsor, and a public-issue resolver. Add a narrowly scoped `start_pool`/`contribute` authorization; never forge a maintainer role or permit a GitHub comment to move money.
3. Build self-service unpaid pool creation from an existing issue URL. Verify installation and owner Copilot readiness before enabling checkout. Add bound confirmation and a separate PayPal order/capture per contributor, with saved keys and verified merchant/amount/reference. Show confirmed total only.
4. Integrate the existing review and selection flow through one winner decision for the issue; atomically freeze the included contribution set at the cutoff. Preserve an existing maintainer-funded bounty as a separately accounted commitment. Add per-capture refund review, exact-cent awards, recipient connection and durable payout reconciliation.
5. Update issue bot status, per-sponsor receipts, read models, dashboard, docs and operations. Test public creation by non-writer without per-issue maintainer action; duplicate pool creation; two and more sponsors; private-data denial; absent app/Copilot consent; capture/merge cutoff races; competing PRs; compatible and incompatible old bounties; claim/payout failures; original-capture refunds; fee shortfalls, reversals and restarts. Then run an explicitly authorized sandbox walkthrough on a real longstanding issue.

## Decisions needed before implementation

The essential choices are now settled by the user's correction: an external actor can start a pool on an existing issue without per-issue maintainer approval, and multiple third parties can add contributions toward the same issue-wide reward. Remaining choices that change the financial guarantee are:

1. When do contributions close, and who bears checkout/payout fees or chargebacks? Is the displayed total an exact amount promised to contributors?
2. Can a pool be funded before the repo owner installs the app and authorizes Copilot, or should it remain an **unfunded draft** until the integration is ready? I recommend no capture until ready so third-party money is not stranded waiting for owner adoption.
3. Can a sponsor also submit a PR and receive the reward? Who may request cancellation, and how do independent refunds work with multiple sponsors?
4. Should sponsor names and individual amounts be public? Are private repositories in the first release?
