## Tasks

### 04.01 — Store identity-bound contributor payout details

**Files:** `packages/server/src/http/connect.ts`, `packages/server/src/actions/connect.ts`, `packages/server/src/db/migrations/0007_phase4_5.sql`, `packages/server/test/integration/connect.test.ts`.

**Depends on:** Phase prerequisites and shared types from Phase 00.

**Interface and implementation contract:** connectContributor(ctx: ActorContext,input: {paypalEmail:string}): Promise<ActionResult<Contributor>>. GitHub ID comes from the session; validate email, require CSRF and encrypt stored payment email using versioned application encryption. This is self-declared sandbox payout information, not verified PayPal ownership.

- [x] Pin the acceptance cases: cannot_connect_for_other_github_id (identity only comes from the session), invalid_email_rejected, csrf_required, email_encrypted_at_rest, and stable GitHub ID across login changes. Tests also confirm raw addresses are absent from the stored display path.
- [x] Implement the contract. Ciphertext is AES-256-GCM with a `v1` envelope and GitHub-ID-bound associated data.
- [x] Verify `connect.test.ts` and complete the actual contributor browser flow; results are recorded in [Phase 4 evidence](../evidence/04-summary.md).

### 04.02 — Show connection status and safe correction behavior

**Files:** `packages/server/src/http/connect.ts`, `packages/server/src/github/comments.ts`, `packages/server/src/actions/connect.ts`, `packages/server/test/integration/connect-status.test.ts`.

**Depends on:** 04.01 and phase prerequisites.

**Interface and implementation contract:** GET /connect shows only the signed-in user's masked destination. Connection confirmation explains that it neither reserves a bounty nor guarantees an award. Updates affect future unsubmitted transfers only; the Phase 06 payout intent snapshots its destination.

**Review completion contract:** Address correction affects only newly created intents; it cannot change an existing unsent or submitted snapshot. Explain that a typo in an existing intent requires investigation; replacement payouts are outside MVP.

### 04.03 — Persist claim-resume events without sending money early

**Files:** `packages/server/src/settlement/claims.ts`, `packages/server/src/jobs/kinds.ts`, `packages/server/src/actions/connect.ts`, `packages/server/test/integration/claim-readiness.test.ts`.

**Depends on:** 04.02 and phase prerequisites.

**Interface and implementation contract:** retryClaims(ghId: string): Promise<void>. Connection enqueues a durable deduped event. Before Phase 06 awards exist, the job is a no-op. Later it resumes only committed awards where every required recipient is connected; it cannot invent/reassign an award.

**Review completion contract:** Do not dedupe all connections in one minute: two payees can connect across a completed no-op and strand an award. Key resume events by committed connection activity/version; Phase 06 also periodically scans AWAITING_CLAIM. Test the same-minute lost-wakeup sequence.

- [x] Pin durable connection-version events and no-award/no-payment behavior. The worker is an intentional no-op until Phase 6 creates award state; each committed connection revision has a distinct dedupe key.
- [x] Implement and verify `claim-readiness.test.ts`; a multiple-recipient award fixture is deferred because the award/allocation schema does not exist yet.
- [x] Update the phase evidence and affected docs/configuration. Commit/push was not requested.
